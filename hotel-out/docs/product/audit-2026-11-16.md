# 前后端检查与修复记录（2026-11-16）

本轮使用 product-delivery-agent，检查搜索、登录刷新、订单与库存相关代码，执行现有测试及新增回归，并使用 Chrome DevTools 实测搜索页面。范围内修复 3 类缺陷；不代表全系统不存在其他缺陷。未改动数据库结构、生产数据或既有服务进程。

## 已修复

| 编号  | 触发条件与影响                                                                                     | 根因                                                            | 修复与验证                                                                                                                                             |

| A3-01 | 浏览器记忆城市为北京，直接打开 `/search`，点击“全部”，城市与列表仍是北京；相同条件重复搜索无法刷新 | 搜索和重置只执行路由跳转，重复导航不会触发 query watcher        | 使用 Vue Router 的重复导航结果识别相同页面，显式同步筛选并重新取数。真实内存路由测试覆盖重置、重复搜索、参数顺序变化；浏览器复现及回归                 |
| A3-02 | 访问令牌刷新尚未返回时退出或切换账号，旧响应会恢复旧会话；旧刷新失败也可能清掉新账号               | 刷新成功直接写入 localStorage，未检查发起刷新时的会话是否仍有效 | 成功或失败处理前比较刷新令牌；会话变化则终止旧请求，不覆盖、清除或重定向新会话。覆盖退出/切换账号与刷新 200、401、503 的 6 种组合                      |

## 实际验证

- 基线：前端 6 个测试通过，lint、build 通过；后端 65 个测试通过。
- 最终：前端 15/15，lint 和 build 退出码均为 0；后端 70/70，0 failure、0 error、0 skipped。
- 后端通过指定本机 JDK 17 执行；测试使用项目配置的 H2 MySQL 兼容模式，并非真实 MySQL 并发压测。
- 浏览器环境：本轮新启动 Vite `http://127.0.0.1:2223`，通过 `/api` 请求既有 8080 后端；不关闭用户原有 2222、8080 服务。
- 修复前：记忆北京后在裸 `/search` 点击全部，localStorage 城市已清空，但目的地仍为北京，首条仍为故宫酒店。
- 修复后：同操作目的地变为全国，首条变为杭州月牙湾，发出 city 为空的新请求并返回 200。
- 相同搜索条件连续点击：URL 不变，酒店请求数量从 4 增加到 5，列表正常。当前搜索页未发现 Console error/warn。
- 审视了窄窗口截图，表单、搜索按钮可见；工具返回实际 CSS viewport 宽度 502，未把它记作 390px 真机验收。
- 未执行本轮新的全角色完整预订、支付、商家及管理员浏览器端到端回归；登录竞争通过可控时序单元测试验证，订单修复通过 Spring 集成测试验证。既有 8080 进程未重启，因此后端修复需正常重启服务后才在该进程生效。

证据位于仓库根目录 `.codex-artifacts/`：

- `audit3-backend-baseline.log`：65 个基线测试。
- `audit3-backend-red.log`：新增 5 个订单校验用例修复前失败。
- `audit3-frontend-red.log`：登录竞争、搜索重置及重复搜索修复前失败。
- `audit3-frontend-final.log`、`audit3-lint.log`、`audit3-build.log`。

## 后续优化建议（未在本轮实施）

| 优先级 | 建议                                          | 代码依据及收益                                                                                                                                                                     | 建议验收                                                                                |
| ------ | --------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| 高     | 生产环境 Redis 故障策略与开发内存回退分开     | `TokenStore` 所有 Redis 异常均静默退回进程内存，而 `RedisProductionValidator` 仅检查启动连接。多实例运行中故障时，共享幂等与会话状态可能分裂；这是代码审查风险，未进行故障注入复现 | 两个实例下断开/恢复 Redis，验证重复下单、令牌轮换，并提供可观测错误；生产故障策略需明确 |
| 中     | 将日期可售查询下推数据库并先缩小候选酒店      | `HotelService.list` 在有日期时先读取所有符合人数/床型的房型，再读整段日历并在 Java 分组。数据量增大时会传输大量无关行，生成较长 IN 查询；本轮未做负载测试                          | 大规模房型/日历数据下看执行计划、内存和 P95，保持分页及跨夜库存语义                     |

| 中     | 搜索时区分加载状态与真实零结果                | 推荐区有骨架屏，结果区仍可能显示上次结果和数量；可加加载反馈或对旧结果标明正在更新                                                                                                 | 慢网、快速切换城市、失败重试均无旧结果误导                                              |
| 中     | 将核心旅程沉淀到持续集成                      | 前端新增测试目前通过抽取 SFC script 执行逻辑，未替代真实组件测试；缺少本轮全角色浏览器回归                                                                                         | 自动跑住客预订/超时、商家确认、管理员退款、跨账号权限，失败保存网络与页面证据           |
